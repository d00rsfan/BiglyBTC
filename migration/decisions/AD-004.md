# AD 004 Compatible persistence foundation

Status: accepted for the bounded configuration/profile-lock foundation; complete
resume, payload layout, recovery and platform qualification remain open.

## Decision and authority

The user requires seamless switching between Java BiglyBT and BiglyBTC using the
same configuration, torrent, resume and temporary payload files, with rollback
without conversion. Keep original filenames, bencoding, binary values, unknown
fields and untouched bytes. Do not introduce an incompatible native-only schema.
Plugin runtime IDs stay unchanged; native project names use BiglyBTC prefixes.

The source baseline is BiglyBT
`cb8c6cb9bb97916cbc7e80338a017200ffc3e71f`: ConfigurationManager, FileUtil,
CoreImpl.canStart, DownloadManagerStateImpl, RDResumeHandler, and FMFileAccess
implementations. The original profile lock is `.azlock`, acquired through Java
FileChannel.tryLock. Keep that lock identity across application names.

## Evidence and selected implementation

[Java/native/Java format evidence](../evidence/P01-03/gcc-interop.json) and the
Clang equivalent prove generated config/backup/recovery/torrent/state round trips,
unknown fields, known integer edits, and preserved original payload bytes. Both
parser/compiler builds and ASan/UBSan/LSan passed their bounded test scope.

Use a bounded C++23 document retaining the original encoding of unchanged nodes.
The production core must not depend on Qt Widgets, OpenSSL, or a torrent engine
for configuration parsing. Promote the tested parser from the feasibility proof
and keep the proof tests exercising that same implementation.

The next bounded adapter uses a held profile lease and original `.saving`/`.bak`
names for writes, file and directory synchronization, and stale-input checks.
Prove the Linux lock conflicts with Java in both directions before enabling
writes. A read of a damaged profile must preserve originals and report the
recovery source. Process-crash tests cannot establish power-loss durability.

## Alternatives and consequences

A separate JSON/native settings schema would require conversion and break the
user's switching workflow; it is excluded by the requirement. Canonicalizing all
metadata risks changing torrent info bytes and losing unknown extensions; retain
raw encodings instead. Reusing the original `.azlock` requires platform-specific
locking adapters and real Java interoperability tests, rather than a private Qt
lock name. Unknown plugin settings remain opaque until their consumers are ported.

## Remaining gates and reversal

Compact/reordered file control data, file links, complete download inventory and
resume semantics, plugin secrets/identities, all setting types, and Windows/macOS
locking/recovery remain assigned to P03/P05/P11. The initial adapter covers
configuration and bounded torrent-state/cache ownership. No live profile or
payload is authorized for testing.
Keep Java files and generated test archives unchanged; removing the new native
implementation does not require reverting a user data conversion.

## Torrent-state ownership checkpoint

The Linux state adapter now passes original Java readback at normal and each
tested save/crash boundary with backup fallback. It hydrates cached attributes,
azp and azpp, persists them and removes only the selected cache entry before
payload mutation. Per-torrent primary replacement has no missing-primary gap.
Backups carry recheck flags, so fallback cannot trust pieces written after the
last metadata commit. Source inspection found that valid=0 alone does not clear
Java PIECE_DONE; conservative ownership sets all flags to PIECE_RECHECK (2),
valid=0, blocks empty and resumecomplete=1. Clean trusted flags require verified
payload flush and the separate session handoff test. Process-crash results do
not establish power-loss durability or qualify other platforms/storage layouts.

## Disposable engine restart optimisation (2026-10-28)

A separate optional `BiglyBTC-mainline.config` may retain bounded native LT DHT runtime state through the held profile lease and existing ConfigFile recovery/CAS. It is disposable implementation cache, never a replacement for original settings, IDs, routing files, torrent/resume state or payload. Missing or corrupt state permits fresh startup only with the identical routing policy; refused or uncertain writes fence further cache publication. Original routing files remain read-only untrusted endpoint hints. This accepts the bounded architectural clarification; Java/LT identity equivalence and broad compatibility gates remain open. Actual qualification belongs to the checkpoint chapter evidence, not this decision.
