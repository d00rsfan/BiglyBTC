# AD 006 Linux delivery and shared plugin installations

Status: Linux-first scope and shared-profile layout selected by the user on
2026-10-17. Later clarification selects temporary private Qt bundling and two CI
variants: bundled Qt now, system Qt once matching packages exist. Packaging
foundation implemented; supported distro/runtime delivery,

does not claim a usable release or a completed updater.

## Release scope and dependency delivery

Concentrate on Linux `.deb`, initially amd64 on the current Ubuntu26.04 development
host. Windows/macOS work is deferred and does not block this first Linux release.
The eventual supported Debian/Ubuntu version range and other architectures remain
to be qualified. Preserve portable service boundaries for future platforms.

Keep two dynamically linked packages behind `BIGLYBTC_BUNDLE_QT`: the initial
default includes private Qt/QPA/Wayland libraries/plugins, translations and the
SDK's required ICU support libraries. The smaller variant uses system Qt when
matching packages become available. The C++ runtime, engine and ordinary OS
libraries remain system supplied in both. Copy the required runtime rather than
the whole SDK. Generate linked
dependencies using `dpkg-shlibdeps` and declare dynamically loaded runtime packages
explicitly. Strip production executables, keep debugging symbols separately, and
measure compressed package bytes, installed application bytes, and additional
dependency downloads separately. Dependencies still need source/license/ABI
provenance even when the package manager supplies them.

Development uses pinned Qt6.12.0 and GCC16/Clang24. Read-only `apt-cache policy`
on this host offered Qt6.10.2+dfsg-7 on 2026-10-17. The `/opt/Qt` SDK is not a
Debian dependency package. Therefore a tiny Qt6.12 application package needs a
qualified source of Qt6.12 runtime packages, a target distro providing them, or a
separately approved/tested lower release Qt baseline. Temporary private bundling
is the user's selected initial solution; the system variant retains this runtime
prerequisite. Do not silently lower the development baseline or bypass missing
dependency metadata. No global packages
are installed as part of this work.

`native/packaging/Debian.cmake` is an opt-in experimental packaging foundation.
It packages executables/notices and the selected Qt runtime under `/usr`, retains
only private relative RUNPATHs when bundling, and preserves the generated-profile
restriction. It overrides CPack's permissive missing-metadata handling with a
strict wrapper: package-local metadata applies only to its own Qt/ICU libraries.
External dependency metadata remains mandatory. Hosted CI uses synthetic
executables; a real Qt fixture additionally proves relocated loader/plugin
resolution and a short offscreen event loop. Neither qualifies a complete
application installation or real compositor session.

## Original updater: inspected behavior

All source references below are original BiglyBT commit
`cb8c6cb9bb97916cbc7e80338a017200ffc3e71f`, not a claim about a later upstream.

- `core/src/com/biglybt/core/util/Constants.java` defines the default catalogue
  base `https://plugins.biglybt.com/`.
- `core/src/com/biglybt/pifimpl/update/sf/impl2/SFPluginDetailsLoaderImpl.java`
  requests `update/pluginlist3.php`, then per-plugin details. Parameters include
  client version, OS/architecture, Java/UI versions and installed plugin versions.
  The version-check service can supply an alternate catalogue base. Catalogue
  refresh is cached with a one-hour minimum reload time.
- `core/src/com/biglybt/pifimpl/update/PluginUpdatePlugin.java` compares installed
  and catalogue versions, selects release/development download URLs, and registers
  downloads with the update manager. Plugins that manage their own updates are
  treated separately. Downloads can use a torrent, a direct URL or a proxy path.
- Installation calls `Update.verifyData`; `pifimpl/local/update/UpdateManagerImpl.java`
  calls `AEVerifier`. A missing signature can be accepted by a verification listener
  only on the non-forced path. This is not an unrestricted unsigned download path.
- Updates install a versioned JAR or unpack a ZIP, handle platform-specific files
  and `plugin.properties`, and may stage actions/restart. ZIP `update.txt` commands
  can remove named files. Java plugin uninstall recursively removes its plugin
  directory (`pifimpl/local/installer/PluginInstallerImpl.java`). Native files in
  that directory consequently share its lifetime; co-location is not protection
  against Java uninstall or plugin-specific cleanup code.

No catalogue request or plugin initialization was run against the user's profile.
These findings come from source inspection only.

## Shared profile, separate executable artifacts

The finished native client resolves the same original profile, normally
`~/.biglybt` on Linux, with the user's explicit original-profile override taking
precedence. Branding does not change it to `.biglybtc`. Original sources are
`core/util/SystemProperties.java` (`azureus.config.path` and migrated aliases) and
`platform/unix/PlatformManagerImpl.java`. Do not rename an old profile as a side
effect of probing. Use the original `.azlock` identity and exclusively own shared
payloads. Java and native must close before handing the profile to the other.
Development builds continue to accept generated fixtures only.

Keep existing plugin directories and Java artifacts. Place native artifacts in a
namespaced child directory, for example:

```text
~/.biglybt/plugins/mldht/
    plugin.properties                 existing Java metadata, untouched
    mldht_<java-version>.jar           existing Java executable, untouched
    <existing plugin data>            compatible settings/data, preserved
    biglybtc/
        installed.json                native version and active artifact identity
        linux-amd64/<abi>/<version>/   native payload and its manifest
```

This is the same plugin folder as the JAR, with native-owned files separated
inside it. Repo `BiglyBTC-plugin-mlDHT` maps to original runtime ID `mldht`; do not
derive case-sensitive IDs or directory names from the repository name. Preserve
an already installed directory's actual name rather than creating a second copy
under a normalized name. Native updates own only their `biglybtc/` subtree, never
Java `plugin.properties`, `plugin.version`, JARs or unrelated files.

The original loader checks a plugin directory for JARs/`plugin.properties` and
`PluginLauncherImpl.getHighestJarVersions` filters `.jar` files. A native-only
child without Java descriptors therefore does not register a Java plugin. Verify
real Java/native discovery and update/uninstall round trips before enabling this
layout in the production host; source inspection is not that runtime proof.
If Java later removes the folder, native discovery reports the missing artifact
and does not recreate it automatically merely because old config keys remain.
Native uninstall removes only native-owned artifacts and preserves Java state.

The shared `PluginInfo.<original-id>.enabled` setting means load at startup; it
does not prove either executable artifact exists. `PluginStateImpl.java` defaults
it to true when absent. Native discovery distinguishes configured/enabled,
Java-installed, native-installed, unsupported and incompatible states. First use
offers/queues verified native counterparts for recognised installed Java plugins
according to the user's install policy; it does not enable disabled plugins,
delete stale plugin settings, or silently install every plugin mentioned in a
config file. Missing/unported native capabilities must be visible before the
user relies on them. Native and Java versions remain independent.

## GitHub Releases and pipeline contract

GitHub Releases are suitable artifact hosting. Fix stable owned repository or
catalogue locations in the client, along with update verification trust roots.
Do not hardcode each new version URL into a new client build. A small signed
catalogue selects immutable versioned release assets for an approved original
plugin ID. `releases/latest/download/<catalogue-name>` can locate a channel
catalogue; it is not sufficient authority or compatibility information for
loading a binary. Per-plugin projects retain `BiglyBTC-plugin-<original name>`.

Signed release metadata must identify the original runtime ID, native release
version, native host API/ABI compatibility, Linux architecture, Qt/runtime build
requirements, asset byte size and SHA256, source commits and artifact URL.
Maintain a monotonic signed catalogue sequence/expiry for replay handling and a
documented recovery path. The user selected repository owner `d00rsfan`. Signing authority/rotation,
and actual release publication remain pending. The five public repositories in
[the rollout](../REPOSITORY_ROLLOUT.md) now exist under `d00rsfan`, created using
authenticated `gh`; only READMEs are published. Catalogue/release assets remain
inactive until signed/qualified. No invented signing key or executable is trusted.

The CI release job must build in a frozen Linux dependency/toolchain environment,
run affected fixtures and shared-profile coexistence tests, verify no bundled
dependencies or developer paths, produce the plugin bundle and dependency/source
manifest, and sign/attest the exact asset. Upload all assets to a draft release
before publication. Enable GitHub immutable releases where available. Separately
update the signed catalogue only after the release asset set is complete. Keep
PR checks read-only; publication jobs run only from the trusted release path with
scoped credentials. This change neither publishes nor creates remote repositories.

The updater must honor original proxy/anonymous-update policy and avoid direct
network fallback. Stage and verify before touching the active plugin. Under the
shared profile lease, install a new version in the native subtree, fsync, and
atomically activate an owned native manifest. Retain rollback metadata/previous
artifact until activation is durable. Never replace a loaded library in place.
Interrupted downloads/installs and a missing dependency leave the old active
plugin usable; reject wrong ID/architecture/ABI, altered bytes and path escapes.
Respect explicit uninstall rather than treating it as first-run repair.

The current SpeedScheduler pilot is a static internal module. Its `.a` is not a
loadable plugin release. AD-003's versioned extension/lifecycle contract must be
qualified before releasing independently loadable modules; avoid exposing C++
standard-library or Qt classes as a cross-version ABI. A versioned C ABI with
explicit ownership/host capabilities is the candidate, not an approved finished
implementation. Pure internal features can ship with the application meanwhile.

Later P02-05 continuation implements experimental shared modules and a C ABI
under [AD-008](AD-008.md), with bounded compiler/sanitizer and original fixtures.
The historical static-pilot observation above is not the current build shape.
Production ABI/update/host integration and complete parity gates remain open.
