BiglyBT public tag-constraint API: null-tag failure and lost evaluation diagnostics

Scope
These are public API reproductions against the retained biglybt-core-3.4.0.1-SNAPSHOT.jar below, on Linux amd64 with OpenJDK26. The small helper targets Java17 (--release17); this is not a JDK17-runtime reproduction. CoreFactory.create() was used after configuration initialisation; Core.start() was never called. Socket creation was denied by an independently checked seccomp wrapper. A fresh private configuration was removed afterwards. No UI reproduction or tag-membership change is claimed.

Observed behaviour
TagManager.compileConstraint(expression) returns a TagConstraint. With an inert DownloadManager supplying all getters needed by these literal expressions:
  contains("HELLO","none|hello")       -> NullPointerException
  contains("HELLO","none|hello",1)     -> NullPointerException
  isEQ(1bad,0)                         -> false; getError() remains null
  contains(1,"x")                     -> false; getError() remains null
The valid single-needle forms are included among32 deterministic boolean observations that succeeded in the same run. Actual Java Pattern primitive checks separately returned true/false for the two alternative patterns. That primitive evidence is not a replacement for the failed public API calls.

Causal evidence
The inspected JAR's public compileConstraint constructs its internal constraint with a null Tag. In the alternatives branch, ConstraintExprFunction.eval unconditionally calls tag_maybe_null.getTagUID() to make the regex-cache key. Its disassembly shows access$6800 followed immediately by Tag.getTagUID at bytecode offsets2643/2646. The evaluator constructs a nonnull HashMap context; supplying a debug/explain context would not repair this null-tag dereference. The public TagConstraint interface has no such overload.

A separate diagnostic problem is visible in the actual JAR: setError(String) starts with aconst_null / putfield error (offsets0..2), rather than retaining the supplied diagnostic. It forwards the text only to a nonnull tag's transient property. getError() reads that error field when compilation succeeded. Consequently the tagless public API loses the invalid-unit/string diagnostics while exposing a normal false result. The existing helper calls getError before and after evaluation, so its recorded false rows establish the null diagnostic dynamically; no reflection or private-field access was used.

Expected behaviour
A supported tagless public evaluator should handle valid contains alternatives without dereferencing an absent tag. Evaluation diagnostics should remain available to public callers, so malformed input is distinguishable from an ordinary false constraint. No claim is made that membership/UI behaviour was reproduced.
